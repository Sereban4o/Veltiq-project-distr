# Лицензирование: онлайн и офлайн

Цель — продавать self-hosted продукт (Laravel + Docker, клиенты Android/Windows) и не давать
пользоваться им без лицензии. Важно понимать: **абсолютной защиты нет** — код, исполняемый на
железе клиента, можно пропатчить. Задача — поднять стоимость обхода, детектировать нарушения и
оставить самое ценное на своей стороне.

## 1. Модель угроз

- **Кто**: клиент, не желающий платить; конкурент; «умелец» с доступом к серверу заказчика.
- **Что защищаем**: право использования (seats/срок/редакция), премиум-функции, white-label.
- **Предел**: полностью локальный код без сети защитить нельзя — только замедлить и заметить.

## 2. Формат лицензии

Лицензия — **JSON/JWT с подписью Ed25519** (в PHP есть `sodium_*`, без зависимостей).
Приватный ключ хранится только у вендора, в продукте — публичный.

```json
{
  "lic": "L-2026-0001",
  "customer": "ACME",
  "edition": "business",
  "features": ["chat", "crm", "mail", "automations", "sso"],
  "seats": 50,
  "not_before": "2026-12-01",
  "expires_at": "2027-12-01",
  "grace_days": 14,
  "servers": ["fp_ab12…", "fp_cd34…"],
  "offline": true,
  "issued_at": "2026-12-01T00:00:00Z",
  "nonce": "…"
}
```

Порядок проверки: подпись → сроки → fingerprint сервера → seats. Всё проверяется **на сервере**;
клиенты ничего не решают.

## 3. Онлайн-лицензирование (phone-home)

- **License server** (вендор): клиенты, лицензии, активации (fingerprint), seats, отзыв.
- Эндпоинты: `POST /activate`, `POST /heartbeat`, `POST /deactivate`, `GET /crl`.
- **Короткоживущий токен** (12–24 ч) с Ed25519-подписью; продукт кэширует его локально и при
  недоступности сети работает до истечения + grace.
- **Heartbeat** (раз в сутки, задача Horizon): license_id, версия, число активных пользователей,
  fingerprint. Ответ — свежий токен либо отказ.
- **Отзыв**: подписанный CRL (онлайн — сразу, офлайн — с окном свежести).
- **Seats**: уникальные активные пользователи за 24 ч; при превышении — мягкий режим (read-only +
  предупреждение), без блокировки данных.

## 4. Офлайн-лицензирование (air-gapped)

Обмен файлами без сети:

1. Админ в продукте генерирует **request-код**: `{fingerprint, nonce, version, date}`.
2. Передаёт вендору (почта/портал).
3. Вендор возвращает **license-файл** с подписью и тем же `nonce` (защита от повторного
   использования чужого файла).
4. Продукт проверяет подпись/срок/fingerprint/nonce.

Дополнительно:
- **Rehost/перенос**: вендор выпускает подписанный release-токен для старого fingerprint и новую
  лицензию.
- **CRL офлайн**: подписанный список отозванных лицензий, загружается вручную.

## 5. Привязка к железу (fingerprint)

- Стабильные, не-PII атрибуты: `machine-id` (Linux), CPU ID, серийник диска, MAC — **хэш** от
  набора, а не сами значения.
- Для VM/контейнеров — «cluster id» из конфигурации (вводится один раз), иначе fingerprint «плывёт».
- Допускать несколько fingerprint-ов (миграция не ломает лицензию), лимит серверов — в токене.
- **Не** привязываться только к MAC/IP.

## 6. Защита от обхода на self-hosted PHP

PHP-код читаем, поэтому уровни:

1. **Проверки в middleware/политиках** для премиум-роутов — базовый уровень (патчится, но отсекает
   случайные попытки).
2. **Компилируемый компонент**: отдельный бинарник (Go/Rust) — «license daemon» — держит публичный
   ключ, проверяет токен и выдаёт краткоживущий «билет» через локальный сокет; PHP вызывает его.
   Патчить вызов сложнее, чем PHP-условие.
3. **Гибрид/SaaS**: самые ценные функции (AI, отчёты, поиск) выполняются у вендора по entitlement
   API. Единственный по-настоящему надёжный вариант.
4. **Целостность**: подписанные релизы (cosign для образов), проверка хэшей критичных файлов при
   старте; при расхождении — предупреждение/аудит, **не** мгновенное «окирпичивание».
5. **Обфускация** (ionCube/SourceGuardian) — только как шум, не как защита.

## 7. Защита от манипуляций со временем

- Хранить `last_seen_at` монотонно (БД + кэш + файл); откат часов назад → флаг/ограничение.
- Онлайн-heartbeat — якорь времени; офлайн — `not_before/expires_at` + «часы не раньше последнего
  запуска».

## 8. Клиенты (Android/Windows)

Основная проверка — на сервере; клиенты не должны быть точкой отказа. Но:
- **Android**: Play Integrity (если через Play) или серверный device-token, привязанный к Keystore;
  подпись APK, проверка `signature` при старте (для sideload).
- **Windows**: подпись MSI/EXE (EV-сертификат); лицензионный ключ, защищённый DPAPI (уже есть);
  опционально TPM-binding; проверка целостности exe.
- White-label/preset-сборки: отдельные ключи/сертификаты на бренд, чтобы утечка одного не
  компрометировала остальные.

## 9. Что не делать

- Не прятать **приватный** ключ в продукте; никаких симметричных секретов в клиенте.
- Не блокировать доступ к данным клиента при истечении — только read-only + уведомления.
- Не собирать телеметрию скрыто; прописать в EULA.
- Не полагаться на один признак (MAC, дата, файл-флаг).
- Не «окирпичивать» при сетевой ошибке — grace обязателен.

## 10. MVP для этого репозитория

1. `App\Services\License\LicenseService` — проверка Ed25519-подписи, сроков, fingerprint, seats
   (libsodium).
2. Публичный ключ в `config/license.php`; приватный — вне репозитория.
3. Fingerprint в `storage/app/.fingerprint` (хэш machine-id + cluster id).
4. Middleware `EnsureLicense` на премиум-группы (`/crm`, `/mail`, `/automations`), мягкий режим.
5. Artisan: `license:request`, `license:activate {file}`, `license:status`, `license:heartbeat`
   (в расписании).
6. Админ-Blade: статус, загрузка файла лицензии, остаток дней, seats.
7. Тесты: подпись/срок/grace/откат часов/превышение seats/чужой fingerprint.
8. Клиенты: без изменений (сервер решает); для онлайн-режима — `GET /api/v1/license/status` для UI.
9. `GET /api/v1/branding` — runtime-тема (см. §12), отдаётся только при наличии entitlement `white_label`.

## 11. Коммерческая страховка

- EULA + право аудита; ответственность за обход в договоре.
- Тарифы с «мягкой деградацией» вместо жёсткой блокировки.
- Аудит аномалий: одна лицензия на множестве fingerprint, откаты часов, повтор nonce.

## 12. Дистрибуция фронтенда и система шаблонов

**Поставка.** Клиенту отдаётся только собранный бандл (`frontend/dist`) внутри Docker-образа вместе
с бэкендом, без исходников SPA. Исходники и **source maps не поставляются**: минификация — не защита,
но source maps сводят барьер на нет за пять минут в DevTools. Дистрибутив собирается скриптом
`scripts/package_distribution.ps1`, который кладёт в бандл только `dist` и одностадийный
`nginx/Dockerfile` (шаблон — `nginx/Dockerfile.dist`).

**Честная формулировка.** SPA исполняется в браузере, поэтому это **не защита от модификации** —
клиент может править `dist/` на своём сервере. Это барьер против форка и ребрендинга «в один клик»
и рычаг удержания. Реальная проверка прав остаётся серверной (§6). В EULA это продаётся как
«официальные сборки и обновления», а не как «защита исходников».

**Разделение кода и брендинга.** Внешний вид описывается **данными, а не кодом**. Паттерн уже есть
для клиентов (`android/branding/*.json`, `scripts/brand`) — расширяем его на web.

Основной путь — **runtime-тема**: сервер отдаёт конфиг через `GET /api/v1/branding`, фронт применяет
его через `createTheme()` (MUI) и CSS-переменные. Смена бренда без пересборки → одна сборка на все
бренды, проще CI и матрица тестов. Build-time тема допустима только как эталонный дефолт образа.

**Реализовано:** публичный `GET /api/v1/branding` (`App\Services\Branding\BrandingService` — строгая
санитизация: hex-цвета, относительные/http(s) URL, ограничение и очистка `customCss`), админ-страница
«🎨 Брендинг» (`/admin/branding`), применение во фронте: палитра/радиусы/шрифт через `createAppTheme`,
плюс title, favicon и `customCss` (в инъектируемом `<style>`). Порядок/скрытие пунктов меню (`menu.order`/`menu.hidden`) применяются в сайдбаре. Гейтинг по entitlement `white_label`
сознательно выключен (лицензирование не внедряем).

```json
{
  "brand": "acme",
  "appName": "Acme Workspace",
  "logo": "/branding/acme/logo.svg",
  "favicon": "/branding/acme/favicon.ico",
  "theme": {
    "palette": { "primary": "#0052CC", "secondary": "#4C9AFF", "mode": "light", "modes": ["light", "dark"] },
    "typography": { "fontFamily": "Inter, sans-serif", "scale": 1.0 },
    "shape": { "borderRadius": 8 },
    "layout": "compact"
  },
  "menu": { "order": ["issues", "boards", "kb", "chat"], "hidden": [] },
  "i18n": { "appTitle": "Рабочее пространство" },
  "customCss": "…"
}
```

**Тёмная тема.** `theme.palette.mode` задаёт тему по умолчанию (`light`, `dark` или `system` — следовать `prefers-color-scheme`), а `theme.palette.modes` — какие темы доступны пользователю. Переключатель темы хранится в клиентских настройках (localStorage/профиль), не требует пересборки и не зависит от бренда: сервер лишь сообщает допустимый набор. Админ-панель продукта использует тот же принцип — переключатель «светлая/тёмная тема» с сохранением выбора и системным дефолтом (`prefers-color-scheme`).

**Разрешено:** палитра (включая светлую/тёмную тему), типографика, скругления, пресет раскладки (энум, не свободная вёрстка),
логотип/фавикон, порядок и скрытие пунктов меню, строки i18n, ограниченный `customCss`.

**Запрещено:** произвольные React-компоненты и «шаблоны-исходники» — это фактически выдача кода,
неподдерживаемые форки и дополнительная XSS-поверхность.

**Реализовано (скины).** Раздел админки «🖌️ Скины» (`/admin/skins`) хранит именованные пресеты оформления
(`App\Models\Skin`: конфиг брендинга + загруженные лого/фавикон). Один скин может быть активным;
применение копирует его конфиг в `settings.branding_config` через `BrandingService`, поэтому клиенты
подхватывают оформление без пересборки. Загрузка логотипа/фавикона (png/jpg/jpeg/webp/ico/svg, SVG
очищается `App\Support\SvgSanitizer`), редактор с живым превью (`public/js/skin-editor.js`,
sandbox-iframe) и пресеты палитры. Логотип и название из брендинга показываются в веб-клиенте (сайдбар,
экран входа) и в самой админ-панели; старая страница «🎨 Брендинг» продолжает работать и ссылается на скины.

**Связка с лицензией.** `white_label` и `extensibility` — лицензируемые `features` в том же JWT
(§2). Сервер проверяет entitlement и только тогда отдаёт кастомную тему; клиенты ничего не решают.
Для брендов — отдельные ключи/сертификаты (§8), чтобы утечка одного не компрометировала остальные.

**Точка расширения (обязательна).** Чтобы не выдавать исходники, но закрыть 80% запросов «под
себя»: встраиваемые виджеты/iframe-панели, кастомные поля и типы сущностей, webhooks + API-токены,
`customCss`, i18n-словари.

**Реализовано (webhooks + виджеты).** `webhooks` (модель, `secret` шифрован, `events`), диспетчер
`WebhookDispatcher` + очередь `DeliverWebhook` (ретраи), подпись HMAC-SHA256 в `X-Veltiq-Signature`,
событие `issue.created/updated/deleted` через observer, админ-страница «🔌 Вебхуки» (CRUD + тест).
API-токены — Sanctum уже есть. Метки меню (`i18n.labels`, ключ → текст) применяются в сайдбаре.
Встраиваемые панели (`WidgetService`, админ «🧩 Виджеты», `GET /api/v1/widgets`, страница `/widgets`)
рендерятся в sandbox-iframe; допускаются только http(s)-URL, список и высота ограничены. Кастомные
поля: админ-конструктор (`custom_fields`, типы text/textarea/number/date/checkbox/select, вариант «список»
с набором значений), выдача определений `GET /api/v1/custom-fields`, запись значений задачи
`PATCH /api/v1/issues/{id}/custom-fields` в `issues.custom_fields` (типы и обязательность проверяются,
неизвестные ключи отбрасываются), панель «Доп. поля» в карточке задачи.

**Целостность и обновления.** Хэш `dist/` фиксируется в релизе, образы подписываются (cosign, §6).
Проверка хэшей при старте → предупреждение и аудит, **не** блокировка (§9).

**Реализовано (хэш бандла).** Сборка пишет `dist/asset-manifest.json` (sha256 по файлам + агрегатный
`bundleId`). Клиент сообщает его в заголовке `X-Veltiq-Bundle`; ожидаемый id фиксируется на деплое
`php artisan assets:pin <id>` (`none` — выключить). Сервер (`VerifyBundleIntegrity` + `BundleIntegrity`)
при расхождении пишет `Log::warning` и запись в аудит-журнал (`assets.integrity_mismatch`, не чаще
раза в час) и **никогда не блокирует** запрос. Подпись образов (cosign) — отложена. Побочный эффект:
правки клиента в бандле затираются обновлением — законный рычаг «берите официальные сборки».

**Санитизация.** `customCss`, URL логотипов и фавиконов из админки — не доверять источнику: лимит
размера, allowlist схем и типов, экранирование.

**Стабильность.** API версионируется (`/api/v1`), иначе кастомные интеграции ломаются и это
становится проблемой поддержки вендора.

## 12.1 Поставка: образ vs исходники

Ключевое различие: §12 — про то, что уходит **заказчику**, а не про то, где ведёт разработку вендор.
Хранить исходники в своём (приватном) репозитории — нормально; клиент получает не репозиторий, а образ.

**Матрица «кто что получает»**

| Модель поставки | Что получает клиент | Барьер «не отдаём код» |
|---|---|---|
| Docker-образы (`pull`/`up`) | `dist` внутри образа, без исходников и source maps | есть (но SPA всё равно читаем) |
| Артефакт-репо `dist` (тег/ветка с предсобранным `dist` + compose/Dockerfile) | бандл + compose, без `src` | есть |
| Source-tarball / ветка с исходниками | весь код (frontend + backend) | нет |
| Клиент собирает из ветки git | весь код | нет |

**Репозитории**
- `product` (приватный): полные исходники, CI, тесты, dependabot. **Никогда не передаётся клиенту.**
- `dist` (клиентский): только `docker-compose.prod.yml`, Dockerfile’ы и/или предсобранный `frontend/dist`,
  скрипты деплоя. Никакой сборки из исходников по месту.

**Режим «только артефакты» (дистрибутив) — внедрён.** Клиентский дистрибутив содержит только
предсобранный `frontend/dist` (без `src/`, без `.map`) и `nginx/Dockerfile`, который только копирует
бандл в `/usr/share/nginx/html` (шаблон — `nginx/Dockerfile.dist`). Node/npm на сервере не нужны,
`docker compose build` не собирает фронтенд из исходников.

1. `VITE_REVERB_KEY` вшивается в бандл при упаковке и должен совпадать с `REVERB_APP_KEY`
   бэкенда; при смене ключа дистрибутив пересобирается.
2. Дистрибутив собирается из приватного репозитория скриптом `scripts/package_distribution.ps1`:
   SPA билдится в Docker на стадии `build` штатного `nginx/Dockerfile`, затем `dist` распаковывается
   в бандл, а `nginx/Dockerfile.dist` становится `nginx/Dockerfile` дистрибутива.
3. В самом репозитории (для команды и CI) `nginx/Dockerfile` по-прежнему собирает SPA из исходников —
   репозиторий клиенту не передаётся.

Альтернатива для CI — публиковать бандл образом (`veltiq-frontend:<ver>`) и копировать
`COPY --from=<registry>/veltiq-frontend:<ver> /dist /usr/share/nginx/html`; версия фиксируется тегом.

**Air-gapped (клиент обязан собирать сам)**
Если отдать исходники неизбежно — это **осознанный отказ от «защиты кода»**. Компенсируем не сокрытием, а:
- серверными проверками прав — единственный по-настоящему надёжный слой (§6);
- лицензией/entitlements — рычаг **сознательно выключен** (по решению продукта лицензирование не внедряем);
- подписью релизов (cosign) и проверкой хэшей при старте — предупреждение + аудит, **не** блокировка (§9);
- EULA + право аудита (§11);
- обновления затирают локальные правки бандла — законный рычаг «берите официальные сборки».

**Итог**
«Не выкладывать фронт на гит» помогает только относительно **публичного** репозитория. Для клиента
же передача ветки с исходниками = передача всего кода. Хотите не отдавать код — отдавайте образы
или предсобранный `dist`, а не ветку с исходниками.

## 12.2 Снижение утечек без PHP-энкодера

Что сделано, чтобы артефакты не отдавали исходники «как есть»:

**Backend-образ** (`backend/.dockerignore`) — из контекста/образа убраны `tests/`, статик-анализ
(`phpstan.neon`, `phpstan-baseline.neon`, `pint.json`), `phpunit*.xml`, `swagger/` (полный API-контракт),
`docs/`, `.github/`, git-hooks. Корневой `.dockerignore` ограничивает контекст сборки nginx-образа
(без `.git`, `android/`, `backend/`, `updates/`, `node_modules`).
PHP всё равно читаем — это уменьшение выдачи, а не защита; реальный рычаг — серверные проверки прав.

**Android** — в `release` включены R8 и удаление неиспользуемых ресурсов:
```kotlin
isMinifyEnabled = true
isShrinkResources = true
```
Переименование и стрип убирают «почти исходники», которые jadx восстанавливает из неминифицированного
dex. Preset-сборка из админки переведена на **Release** (`assembleSelfupdatePresetRelease`); если в
секретах репозитория есть `ANDROID_KEYSTORE_BASE64` (и пароли), APK попутно подписывается.
Артефакт проверки: `app/build/outputs/mapping/selfupdateStandardRelease/mapping.txt`
(`com.tasksbase.chat.realtime.RealtimeClient -> z2.c`).

## 12.3 Компилируемый core-сервис (Go) — пилот

Второй путь вместо PHP-энкодера: ценная логика уезжает в **компилируемый сервис** (``core/``, Go,
только stdlib), а PHP остаётся тонким слоем. Сервис поставляется бинарником — исходников Go в образе
нет, реверс дорогой и не даёт «почти исходников».

**Пилот:** алгоритм поиска свободных окон календаря (`FreeSlotFinder`), **движок автоматизаций
задач** (`TaskAutomationEngine`), **автоматизации CRM** (`CrmAutomationService`), **разрешение прав**
(`PermissionService`), **правила почты** (`MailRuleEngine`), **развёртка RRULE** (`RecurrenceExpander`),
**сниппеты/окно поиска** (`GlobalSearchService`) и **агрегация табеля** (`TimesheetController`). Доступ к БД и запись эффектов
остаются в PHP: наружу уходят только интервалы занятости, снимки задач/сделок с правилами, записи
о трудозатратах и предвычисленные входы решения о правах (роль, оверрайды, baseline, права роли).

**Контракт:**
- `POST /v1/calendar/free-slots` — `{window_start, window_end, duration, meetings[]}` → `{slots:[{start,end}]}`;
- `POST /v1/tasksbase/automation/match` — `{issue, context, rules[]}` → `{matches:[{rule_id, actions[]}]}`;
  сервис сам отбрасывает неизвестные действия (`delete_issue` и т.п.) и невалидные приоритеты, так что
  кривое правило не протащит неожиданный эффект;
- `POST /v1/tasksbase/timesheet` — `{entries[]}` → `{total_seconds, total_hours, days[]}` (группировка
  по дням, суммы и округление);
- `POST /v1/crm/automation/match` — `{deal, context, rules[]}` → `{matches:[{rule_id, action}]}`;
- `POST /v1/permissions/resolve` — предвычисленные входы → `{allow, reason}` (порядок: admin → gate →
  scope deny/allow → global deny/allow → baseline → права роли);
- `POST /v1/mail/rules/resolve` — `{rules[], message}` → `{rule_id}|null` (первое совпадение; группы
  all/any, поля from/to/subject/body, contains/equals, вложения; `regex` не отправляется);
- `POST /v1/calendar/expand-recurrence` — `{start, duration_seconds, rrule, exdates[], from, to, limit,
  timezone}` → `{items[], truncated}`; поддерживаются DAILY/WEEKLY/MONTHLY/YEARLY с INTERVAL/COUNT/UNTIL/
  BYDAY (включая `2TU`, `-1FR`)/BYMONTHDAY/BYMONTH/WKST и EXDATE; остальное (BYSETPOS, BYYEARDAY,
  BYWEEKNO, суб-дневные частоты) отвечает **501** — PHP остаётся на своей реализации (Sabre).
- `POST /v1/search/snippets` — `{query, length, texts[], window:{per_page,page}}` → `{snippets:{key:value},
  window}`: батч сниппетов (совпадение без учёта регистра, центрированный фрагмент, эллипсы — по рунам)
  и размер окна кандидатов.

**Parity-тесты.** `CoreParityTest` и `CoreParityMatrixTest` (@group parity) прогоняют одни и те же
сценарии через оба движка и сравнивают результаты: RRULE, свободные окна, табель, правила почты,
права и автоматизации задач/CRM. Без запущенного core тесты скипаются, поэтому обычный прогон не
зависит от окружения. Именно parity-тест поймал расхождение: Sabre всегда включает сам DTSTART, даже
когда BY*-фильтры его не отбирают — Go-движок теперь делает так же.

Аутентификация — общий секрет в заголовке `X-Core-Token` (сравнение constant-time). Без токена сервис
**не стартует**; порты наружу не публикуются (только Docker-сеть), для compose есть healthcheck `/healthz`.

**Fail-open:** `App\Services\Core\CoreClient` возвращает `null` при выключенном сервисе, ошибке или
таймауте (по умолчанию 3 с) — вызывающие молча считают локально. Продукт работает и без контейнера.
Ответы сервиса нормализуются к тому же ISO-формату, что и PHP-путь.

**Breaker и наблюдаемость.** После `CORE_BREAKER_THRESHOLD` (5) подряд транспортных ошибок вызовы
пропускаются на `CORE_BREAKER_COOLDOWN` (60 с) без сетевой попытки; первый успех закрывает breaker.
Каждый переход на PHP считается (`core:fallback:*`), состояние видно командой `php artisan core:stats`
(`--reset` чистит счётчики и закрывает breaker). Все запросы проходят через один `post()`: enabled-проверка,
breaker, таймаут, лог и учёт — чтобы новый блок не забыл какой-то из слоёв.

**Запуск:**
```bash
# dev
CORE_TOKEN=dev-core-token docker compose up -d core app worker
# prod (backend/.env.production: CORE_URL=http://core:8080, CORE_TOKEN, CORE_TIMEOUT,
#       CORE_BREAKER_THRESHOLD, CORE_BREAKER_COOLDOWN)
docker compose --env-file backend/.env.production -f docker-compose.prod.yml up -d
# наблюдение
php artisan core:stats
```

**Тесты:** Go — `go vet`, `go test -race` и `golangci-lint` (CI-джоба `core`, конфиг `core/.golangci.yml`),
PHP — `CoreServiceTest`, `CoreAutomationTest`, `CoreTimesheetTest`, `CoreExtrasTest`, `CoreMailRulesTest`,
`CoreRecurrenceTest`, `CoreSearchTextTest`, `CoreBreakerTest` (результат из сервиса, fallback, breaker,
счётчики), плюс parity-набор и существующие PHP-тесты на локальной реализации.

**Осталось в PHP (осознанно):** ранжирование поиска (сращено с Meilisearch — снаружи вынесена только
текстовая часть: сниппеты и окно кандидатов) и агрегация календаря (сборка из БД); условия почты
с `regex` тоже остаются в PHP (RE2 ≠ PCRE).
